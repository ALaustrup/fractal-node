# ADR-0013 — React + TypeScript + Vite for the Phase 1 Web GUI

**Status:** Accepted
**Date:** 2026-09-03
**Deciders:** Andrew
**Phase:** 1

## 1. Context

`02 §2` fixes the spine sentence: a Citizen can create a Society, talk in it, store things in it, earn Fraction in it, and govern it — from a web GUI, a CLI, or an API, with an Agent helping. Phase 1 must therefore ship a **working GUI to the widest possible audience with zero install**, and `34 §4.2` places the web target there for that reason.

The web front end is also load-bearing beyond web. `34 §2.3` budgets the same React codebase across web, PWA and three desktop targets — 26% of desktop source, shared. Choosing the web framework is therefore choosing the presentation stack for five of eight targets, and ADR-0012's desktop economics depend on it.

Two hard constraints narrow the field. **N8 makes WCAG 2.2 AA a floor with AAA text contrast in the default theme**, and `34 §4.2` names the web target the reference accessibility implementation for the whole product — axe-core in CI on every route and every dialog, manual VoiceOver/NVDA audits per phase gate. And `32 §8` sets CI-enforced budgets: 2.5s TTI at p75 on mid-tier hardware, ≤180 KB gzipped initial JS, ≤60 KB per route chunk — on top of a 1.4–1.8 MB gzipped wasm core.

Note what is *not* in scope. Domain logic is Rust (`34 §I1`); the front end is presentation over `fractal-core-wasm` in a dedicated Worker with OPFS-backed SQLite. This decision is about a rendering and component layer, not about where rules live.

## 2. Decision

The Phase 1 Web GUI is **React 18 + TypeScript + Vite**, with TanStack Router, consuming the core as a lazily-loaded wasm module in a dedicated Worker. The same codebase serves the PWA (Phase 3) and the Tauri desktop shells (Phase 2 and 5). Components compose exclusively from LATTICE design tokens (`32 §2`) generated by `cargo xtask tokens` — a Rust pipeline, deliberately, so the CLI never needs a JS toolchain. TypeScript runs under the `40 §3` standards; no business rule may be implemented here.

## 3. Consequences

### Positive
- The largest talent pool of any front-end technology, which matters most for the phase that must ship fastest.
- The most mature accessibility tooling in existence: axe-core, testing-library's accessibility-first queries, react-aria primitives, and an enormous corpus of documented ARIA patterns. N8 is a floor we can actually hold, and holding it is a phase gate.
- One presentation tree serves five targets, which is the assumption ADR-0012's 88% shared-source figure rests on.
- Vite gives fast HMR and a build that handles wasm and Worker bundling without custom plumbing.

### Negative
- **Bundle discipline is a permanent tax.** React plus a router plus the component inventory of `32 §5` sits uncomfortably close to a 180 KB budget that also carries a 1.4–1.8 MB wasm core. Every route is code-split, every dependency is justified, and the bundle analyzer is a required check rather than a diagnostic.
- React's runtime overhead is real on the two hottest surfaces in the product — a virtualized Chamber list and a composer under IME — and both need virtualization and careful memoization rather than idiomatic React.
- The ecosystem churns. A five-year maintenance horizon in React means periodic migrations that deliver no user value.
- TypeScript is not memory- or numerically-safe, which is why `34 §I1` confines it to presentation and why a lint scans shell code for domain-rule identifiers.

### Neutral / follow-on work
`41 §10.1` fixes the web app's layout; `32 §11` requires every component to carry an anatomy, all nine states, a keyboard contract, an ARIA contract, a token map, a CLI equivalent and a visual regression test before it exists.

## 4. Alternatives Considered

| Alternative | Why it was plausible | Why rejected |
|---|---|---|
| **Svelte or SolidJS** | Materially better runtime characteristics and smaller bundles — both would sit more comfortably inside the `32 §8` budgets, and the reactivity model suits a Signal-driven UI | Smaller accessibility ecosystem. N8 is non-negotiable and `34 §4.2` makes web the reference a11y implementation for every other target; the tooling and audited-pattern corpus for React is a category ahead, and choosing a runtime win over an accessibility floor inverts the `00 §2` conflict order. Hiring pool is a secondary but real factor for the phase that must ship fastest |
| **Leptos or Dioxus (Rust-native front end)** | Genuinely tempting: one language end to end, no wasm/JS boundary for the presentation layer, and the core is already Rust | Immature accessibility tooling. There is no axe-equivalent integrated into the test loop and no comparable corpus of audited ARIA patterns, which jeopardizes N8 directly. `10 §12` keeps Dioxus/Freya named as the *desktop-only* fallback if webview regressions break the P10 budget — a narrow, later, better-informed decision than adopting it for the target that must ship first |
| **Plain web components, no framework** | Zero framework bytes, no ecosystem churn, native browser primitives, perfect longevity | Shifts the entire cost onto us: state management, routing, list virtualization, focus management and form semantics all become first-party code, and each is a place to get accessibility subtly wrong. `02 §5`'s complexity budget is better spent on the Runtime than on rebuilding a framework |
| **Server-rendered HTML with progressive enhancement** | Fastest first paint, smallest client, oldest and most reliable accessibility story | Incompatible with P2. The web target holds a local replica in OPFS-backed SQLite and must render every core surface offline (`34 §12.1`); a server-rendered app has no offline read path. It also cannot host the wasm core as the desktop shells do, so the shared-presentation economics collapse |

## 5. Exit Cost

**14–20 engineer-weeks to replace the presentation layer at the Phase 3 surface, and it rises with every shipped screen.** The work: reimplement the `32 §5` component inventory against the new framework with all nine required artifacts each (~8 weeks); re-do routing, list virtualization, focus management and the four mandatory data-surface states (~4 weeks); re-establish the axe-core and visual-regression suites (~3 weeks); re-integrate the wasm core bindings and the Worker/OPFS plumbing (~2 weeks). The design tokens survive untouched — they are generated from `design/tokens/` by a Rust pipeline (N7) — and so does the core. That containment is the reason this number is bounded rather than open-ended.

## 6. Principle Served

**P10** in its accessibility half — the mature a11y ecosystem is the reason this choice wins, and N8 is the gate. **P13** and **N2**, since one presentation tree across five targets is what makes them affordable. **P3**, since the GUI consumes the same public API a third party would. Traded: raw runtime performance against Svelte/Solid, which `00 §2` permits because P10's performance half is enforced by budgets rather than by framework choice, and the budgets are met with discipline.

## 7. Falsification Test

1. **Accessibility gate**: axe-core runs in CI on every route and every dialog and blocks merge on any violation; manual VoiceOver/NVDA audits run per phase gate. A merged PR that regresses a11y without an approved exception is the violation.
2. **Performance budgets**: Lighthouse CI enforces FCP ≤1.2s and TTI ≤2.5s p75 on mid-tier hardware; the bundle analyzer enforces ≤180 KB gzipped initial JS and ≤60 KB per route chunk. Budget regression fails the build (`32 §8`).
3. **No business rules in TypeScript** (`34 §I1`): a lint scans `apps/web` for forbidden identifiers — balance arithmetic, XP or Trust computation, capability intersection, conflict resolution — and fails on a hit.
4. **No back doors** (P3): grep the client for any database driver, direct queue access, or HTTP path absent from the schema registry. Each hit is a violation.
5. **No literal colour** (N7): stylelint `color-no-hex` with a one-file allowlist; the token regeneration diff must be empty.

## 8. Maintenance Horizon

React is maintained by Meta with a large independent contributor base and a long deprecation runway; TypeScript by Microsoft; Vite by a foundation-backed community with commercial sponsorship. None is single-maintainer critical-path. The concentrated risk is the long tail of component libraries, which `40 §10.2` governs through `cargo-deny`'s npm equivalent, a licence allowlist and the `02 §5` five-dependencies-per-phase budget. We deliberately do not depend on a component framework for the design system: LATTICE components are first-party over generated tokens, so a framework migration does not take the visual language with it.

## 9. Review Trigger

Reopen if (a) the initial JS budget cannot be held for two consecutive releases without disabling a `32 §5` component, which means the framework's floor no longer fits the product; (b) INP p95 exceeds 100ms on the Chamber surface after virtualization and memoization work, which would indicate a runtime ceiling rather than an implementation gap; or (c) a Rust-native front-end stack reaches accessibility-tooling parity — an axe-equivalent in the test loop and an audited ARIA pattern corpus — at which point the `10 §12` desktop-only evaluation becomes a whole-product question.
